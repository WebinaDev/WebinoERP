# هاب جامع ارتباطات چندکاناله سازمانی (Enterprise Communication Hub Architecture)

این سند معماری و موتور اورکستراسیون یکپارچه ارتباطات و پیام‌رسانی سازمانی (**Event → Policy → Template → Fanout → Delivery Ledger**) در **WebinoERP** را تبیین می‌کند.

---

## ۱. چرخه اورکستراسیون پیام و پالیسی گیت (Policy Engine)

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ 1. رویداد سیستمی در ماژول‌ها (Event Catalog: order.paid, invoice.overdue)    │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 2. بررسی پالیسی و ممانعت از ارسال تکراری (Deduplication Window)              │
│    • محاسبه هش یکتا از متن، کاربر و رویداد (`dedup_hash`)                   │
│    • مسدودسازی پیام‌های مشابه در بازه زمانی ۱۰ دقیقه‌ای                     │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 3. بازرسی ساعات سکوت کاربر و اولویت پیام (Quiet Hours Gate)                 │
│    • پیام‌های با اولویت `critical` همیشه ارسال می‌شوند.                     │
│    • سایر پیام‌ها در ساعات استراحت کاربر (`quiet_hours`) معلق می‌شوند.      │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 4. موتور انتشار چندکاناله هوشمند (`NotificationFanout`)                      │
│    ├─ In-App   : اعلان بلادرنگ درون سیستم (`CoreNotification`)             │
│    ├─ Email    : ایمیل تراکنشی معتبر با قالب برندشده سازمانی                 │
│    ├─ SMS      : مدیرپیامک خدماتی با پترن مصوب و کنترل سقف ارسال             │
│    └─ Chat     : پل ارتباطی بله (Bale)، تلگرام و اسلک                        │
└──────────────────────────────────────┬──────────────────────────────────────┘
                                       │
                                       ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│ 5. ثبت دفتر کل تحویل واحد (`channel_deliveries` Ledger)                     │
│    • ثبت وضعیت دقیق: `delivered`, `sent`, `suppressed`, `failed`            │
│    • ثبت گیرنده، زمان دقیق تحویل (`delivered_at`) و علت‌های بلاک            │
└─────────────────────────────────────────────────────────────────────────────┘
```

---

## ۲. مشخصات جداول هاب ارتباطات

- **`communication_event_catalog`**: کاتالوگ استاندارد رویدادهای کسب‌وکار با تفکیک پیام‌های تراکنشی از تبلیغاتی.
- **`communication_templates`**: نگاشت رویداد به قالب پیام در هر کانال همراه با پترن پیامک خدماتی.
- **`user_notification_preferences`**: ترجیحات اختصاصی کاربر برای فعال/غیرفعال کردن کانال‌ها و تعیین ساعات سکوت.
- **`channel_deliveries`**: دفتر کل واحد حسابرسی تحویل پیام‌ها با فیلدهای `dedup_hash`, `recipient`, `delivered_at`.

---

## ۳. اندپوینت‌های وب‌سرویس

- **`GET /api/v1/integrations/communication/events`**: فهرست رویدادهای استاندارد فعال سیستم.
- **`GET /api/v1/integrations/communication/templates`**: دریافت قالب‌های فعال پیام‌ها.
- **`POST /api/v1/integrations/communication/dispatch`**: ارسال پیام با رعایت کامل پالیسی و لاگ در دفتر کل تحویل.
- **`POST /api/v1/integrations/communication/preferences`**: ذخیره و تنظیم ساعات سکوت و ترجیحات کانال‌های کاربر.
