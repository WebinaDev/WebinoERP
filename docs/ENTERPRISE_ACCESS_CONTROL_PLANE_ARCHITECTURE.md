# معماری موتور جامع مدیریت و کنترل دسترسی وبینا (Webino Access Control Plane)

این سند فلسفه، مدل ۴ لایه امنیتی، کاتالوگ اتمی دسترسی‌ها، قوانین حوزه داده (Scope)، امنیت سطح فیلد (Field-Level Security)، سیاست‌های شرطی (ABAC)، و شبیه‌ساز دسترسی در سامانه **WebinoERP** را تشریح می‌کند.

---

## ۱. فلسفه و قانون طلایی دسترسی در وبینا

> **قانون طلایی**:
> هر درخواست API و هر کنش UI باید الزاماً از یک موتور ارزیابی واحد `AuthorizationEngine::authorize()` عبور کند. هیچ ماژولی حق ندارد دسترسی را به صورت مجزا، پراکنده یا با بررسی ساده فیلد نقش (`if role == 'manager'`) کنترل کند.

مدل دسترسی وبینا ترکیبی از **RBAC + ABAC + Data Scope + Field Policy** روی ۴ لایه اساسی است:
1. **چه کسی (User / Membership)**: احراز هویت و عضویت فعال کاربر در شرکت یا هلدینگ.
2. **در کدام سازمان (Company / Branch)**: تفکیک دقیق مرزهای داده شعب و شرکت‌ها.
3. **روی چه چیزی (Resource / Record)**: کنترل مالکیت رکورد (`owned_by`, `branch_id`, `warehouse_id`).
4. **چه کاری و چه اثری (Action / Field / Effect)**: اجرای کنش‌های اتمی (`sales.invoice.approve`) با اولویت مطلق قانون **Deny برنده است**.

---

## ۲. جریان ارزیابی در موتور تصمیم‌گیری (Decision Pipeline)

```
[درخواست کلاینت / API / رویداد ماژول]
       │
       ▼
1. احراز هویت کاربر (Authentication)
       │
       ▼
2. تشخیص زمینه سازمانی فعال (Company / Branch Membership & Delegation)
       │
       ▼
3. بررسی استثنائات مستقیم کاربر (User Direct Deny همیشه مقدم است)
       │
       ▼
4. تجمیع نقش‌های سازمانی (User Roles) و بررسی وجود Deny در نقش‌ها
       │
       ▼
5. تطابق کد مجوز اتمی (`module.resource.action`)
       │
       ▼
6. ارزیابی حوزه داده (Scope: all | branch | own | team | custom_filter)
       │
       ▼
7. ارزیابی سیاست‌های شرطی پویا (ABAC: سقف مبلغ فاکتور، ساعات مجاز)
       │  ├─ سقف رعایت شده ───────► ALLOW
       │  └─ سقف فراتر رفته ──────► ALLOW_WITH_APPROVAL (ارجاع خودکار به کارتابل گردش کار)
       ▼
8. اعمال فیلتر سطح فیلد (Field-Level Security: Hide یا Mask قیمت خرید/شبا)
       │
       ▼
9. ثبت در دفتر ممیزی غیرقابل تغییر (`authz_access_logs`)
       │
       ▼
[پاسخ نهایی: Allow / Deny / AllowWithApproval به همراه الزامات MFA و Reason]
```

---

## ۳. استاندارد ماتریس اکشن‌ها (Atomic Actions)

- `view`: مشاهده لیست و فرم جزئیات.
- `create`: ایجاد سند خام.
- `update`: ویرایش فیلدهای مجاز.
- `delete`: حذف ردیف یا سند.
- `approve`: تأیید نهایی یا صدور مجوز عملیاتی.
- `void`: ابطال رسمی اسناد مالی/انبار.
- `export`: دریافت فایل اکسل/CSV.
- `view_cost`: مشاهده بهای تمام‌شده و حاشیه سود (مجوز حساس).
- `edit_price`: تغییر قیمت مصوب کالا در فاکتور.
- `edit_discount`: اعمال تخفیف تا سقف تعیین‌شده در سیاست ABAC.

---

## ۴. امنیت سطح فیلد (Field-Level Security)
پاسخ‌های API در سرور پردازش شده و فیلدهای حساس پیش از ارسال به کلاینت فیلتر می‌شوند:
- `sales.invoice.cost_price`: در صورت فقدان مجوز `sales.cost.view` فیلد به کلی **حذف (hide)** می‌شود.
- `acc_cash_accounts.sheba`: برای کاربران بدون دسترسی تراز مالی شماره شبا به صورت `IR************1234` **ماسک (mask)** می‌شود.

---

## ۵. شبیه‌ساز دسترسی (Permission Simulator)
در تب شبیه‌ساز پنل مدیریت دسترسی (`/authz/simulator`)، مدیران سیستم می‌توانند هر سناریوی ترکیبی (کاربر، نقش، شعبه کاربر، شعبه رکورد، مبلغ فاکتور) را تست کرده و علت رد یا تأیید درخواست را به همراه زنجیره کامل سیاست‌ها مشاهده نمایند.
